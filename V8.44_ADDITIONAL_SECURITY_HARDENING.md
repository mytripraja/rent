# Rental Manager V8.44 — Additional Security Hardening

## Purpose
Follow-up security audit after V8.43. This release fixes three concrete authorization/data-integrity issues found during review.

## Fixes

### 1. Rent agreement permission enforcement
`api/get-agreement-url.js` now checks tenant `rent` and `rentDetails` permissions before issuing a signed Cloudinary URL for a tenant's agreement.

A tenant whose rent access or rent-details access is disabled cannot bypass the UI by calling the signed-URL endpoint directly.

### 2. Directory mirror is owner-managed
The Firestore rule for `/directory/{houseId}` no longer permits tenants to write directory records.

Tenants can still read the directory when the `directory` permission is enabled, but cannot alter their house's directory name, phone, status, or other mirrored fields through a direct Firestore write.

### 3. Family-account creation rollback
`api/create-subtenant.js` now removes the newly created Firebase Auth user if Firestore profile creation or the house counter update fails.

This prevents an orphaned Auth account with no usable Firestore profile.

### 4. Family-account deletion cleanup
`api/delete-subtenant.js` now uses an atomic Firestore increment/decrement approach for the family-account count and treats post-Auth cleanup as retryable. It never recreates deleted credentials silently.

## Verification

- All JavaScript files passed `node --check`.
- Targeted modified API files passed syntax validation.
- No private Firebase service-account key, Cloudinary secret, or private key was found in the shipped project.
- Firebase CLI was unavailable, so Firestore Emulator/rules deployment validation was not possible in this environment.
- Frontend production build was not claimed because `node_modules` is absent in the environment.
